# Developer Handoff

You've received this repository (as a ZIP, a clone, or otherwise) and need
to understand it well enough to run it and safely change it, without the
conversation history that produced it. This document is that bridge.

## If you received this project as a ZIP

Exact sequence:

1. Extract the ZIP.
2. Install prerequisites — [SETUP.md, Part A](SETUP.md#part-a--before-starting-verify-prerequisites).
3. Read [`../README.md`](../README.md).
4. Read this document's [What to read first](#what-to-read-first) section below.
5. Configure environment files — [SETUP.md, Part C](SETUP.md#part-c--environment-configuration).
6. Install dependencies — [SETUP.md, Part D](SETUP.md#part-d--install-dependencies).
7. Start infrastructure (MongoDB, Redis ×2, Qdrant, Ollama) — [SETUP.md, Parts E–F](SETUP.md#part-e--start-infrastructure-first).
8. Start Team4A — [SETUP.md, Part G](SETUP.md#part-g--start-team4a-terminal-1).
9. Start Team4B — [SETUP.md, Part H](SETUP.md#part-h--start-team4b-terminal-2).
10. Start Team4C — [SETUP.md, Part I](SETUP.md#part-i--start-team4c-terminal-3).
11. Perform the smoke test — [SETUP.md, Part L](SETUP.md#part-l--first-time-end-to-end-smoke-test).
12. Read [ARCHITECTURE.md](ARCHITECTURE.md).
13. Read [INTEGRATION.md](INTEGRATION.md).
14. Read [TESTING.md](TESTING.md).
15. Read [TROUBLESHOOTING.md](TROUBLESHOOTING.md) — even before you hit a
    problem, so you recognize the common ones on sight.

## If you cloned this project from GitHub

Same sequence as the ZIP case above, with two differences:

1. `git clone <repository-url> EduCopilot-M6-Local && cd EduCopilot-M6-Local`
   instead of extracting a ZIP.
2. **You will not receive any `.env`/`.env.local` file, any `*.pem` key
   file, `node_modules/`, either service's Python virtual environment,
   `team4c/.next/`, or `team4c/test-results/`/`playwright-report/`** — all
   of these are intentionally excluded from version control (see
   `.gitignore` at the repository root and in `team4c/`). This is
   expected, not a broken checkout. You create your own environment
   files from the `.env.example` templates and generate your own local
   secrets (`AUTH_SECRET`, the service-JWT keypair) — see
   [SETUP.md, Part C](SETUP.md#part-c--environment-configuration). Never
   ask another developer for their real `.env` file or copy one from
   anywhere else; generate your own.

From step 2 onward ("Install prerequisites"), follow the exact same
sequence as the ZIP case.

### What is intentionally not included in the repository

| Not included | Why | How you get it |
|---|---|---|
| `.env`, `.env.local` (real values) | Secrets — never belong in version control | Copy from `.env.example` and fill in your own values ([SETUP.md](SETUP.md)) |
| `*.pem` key files | The service-JWT signing keypair is a secret | Generate your own ([SETUP.md, Part C](SETUP.md#part-c--environment-configuration)) |
| Passwords, API keys, tokens | Secrets | You generate/obtain your own for local development |
| `node_modules/` | Generated, huge, reproducible from `package.json` | `npm install` |
| Python virtual environments (`.venv/`, `venv/`) | Generated, reproducible from `requirements.txt` | `pip install -r requirements.txt` |
| `team4c/.next/` | Next.js's generated build cache | Regenerated automatically by `npm run dev`/`npm run build` |
| `team4c/test-results/`, `playwright-report/` | Generated Playwright run artifacts | Regenerated by `npx playwright test` |
| Local database contents (MongoDB, Qdrant, Redis data) | Your own local infrastructure's data, not project source | Created as you use the running product locally |
| Docker container/volume state | Local infrastructure, not project source | Created by the `docker run`/`docker compose` commands in [SETUP.md](SETUP.md) |

If you ever find one of the above tracked in git, treat it as a real
incident (especially for the first three rows) — see
[SECURITY.md](SECURITY.md).

## How to safely modify code

1. Identify which service the change belongs to. If it seems to need
   changes in two services, re-check [INTEGRATION.md](INTEGRATION.md)
   first — the contract between services is deliberately narrow, and a
   change that seems to require touching both sides often means the
   change belongs entirely on one side.
2. Read that service's own doc (`TEAM4A.md`/`TEAM4B.md`/`TEAM4C.md`) and
   the relevant source before changing anything.
3. Make the smallest change that achieves the goal. Don't refactor
   unrelated code in the same change.
4. Run that service's validation (below) before considering the change
   done.
5. If the change touches Team4B's retrieval/generation configuration
   (`top_k`, `score_threshold`, the embedding model, RRF settings, the
   reranker), read [RAG_ARCHITECTURE.md](RAG_ARCHITECTURE.md) first — this
   configuration is explicitly frozen based on real evaluation, and every
   past attempt to change it without new evidence was reverted. Don't
   change it without the same standard of evidence that arc used.


## What must not be modified casually

- **Team4B's frozen retrieval/generation configuration** (see above) —
  changing it without the evaluation rigor that froze it in the first
  place risks silently regressing accuracy that was hard-won across a
  multi-phase validation arc.
- **The service JWT contract** (`aud`/`scope`/`iss` claims, which key is
  public vs. private) — a mismatch here fails closed (requests get
  rejected), which is the safe failure mode, but it's easy to break
  silently if you're not looking at [INTEGRATION.md](INTEGRATION.md)
  first.
- **`File.currentIngestionGeneration`** — Team4A writes it, Team4B reads
  it, Team4C owns the schema. Don't repurpose this field for anything
  else; the generation/authority mechanism depends on it meaning exactly
  one thing.
- **The `MONGO_DATABASE_NAME` invariant** across Team4A/Team4B/Team4C —
  see [ENVIRONMENT.md](ENVIRONMENT.md), "Cross-service invariants" section.
- **Qdrant collections** — don't recreate or delete a collection to "fix"
  something; see [TROUBLESHOOTING.md](TROUBLESHOOTING.md).

## Important architectural invariants

- `workspace_id` is mandatory on every Team4B retrieval code path — there
  is no "search everything" option, and none should ever be added.
- A citation is only ever built from retrieval metadata, never from the
  model's own free-text output.
- Retrieved document content is untrusted data in the prompt, never a
  trusted instruction — see [SECURITY_ARCHITECTURE.md](SECURITY_ARCHITECTURE.md).
- Team4C independently re-verifies workspace ownership and citation
  safety even when Team4B has already scoped/filtered something —
  defense-in-depth, not redundant paranoia to be "simplified" away.

## Common mistakes

- Starting Team4A with its *default* `MONGO_DATABASE_NAME` instead of
  overriding it to match Team4C's database — the single most common
  local-setup failure. See [TROUBLESHOOTING.md](TROUBLESHOOTING.md).
- Forgetting Team4B's Redis is on a **different port (6380)** from
  Team4A's Redis (6379) — they are two separate instances.
- Assuming a fast AI Tutor response in testing — local LLM generation is
  CPU-bound in this environment and can take 30–140+ seconds; design any
  new timeout/loading-state logic around that reality, not an assumption
  of sub-second responses.
- Treating Team4B's own `QDRANT_COLLECTION_NAME` default as the collection
  that matters — production traffic actually depends on whichever
  collection Team4A's `CANONICAL_QDRANT_COLLECTION_NAME` publishes to;
  the two must be aligned (see [ENVIRONMENT.md](ENVIRONMENT.md)).
- Reading a `docs/PHASE_6*`-style historical report (if you find one still
  referenced somewhere) as current status — always prefer this document
  set (`README.md`, `ARCHITECTURE.md`, `TEAM4A/B/C.md`, `M6_STATUS.md`)
  over any phase-specific report for current state.

## How to prepare a pull request

1. Run the full validation for whichever service(s) you touched (§ How
   to run validation, above) — don't open a PR on a red suite.
2. Confirm you haven't introduced a *new* ESLint/pytest issue — compare
   against the baselines in [TESTING.md](TESTING.md), since a small
   number of pre-existing issues are expected and shouldn't be conflated
   with something you caused.
3. If your change crosses a service boundary (touches the service-JWT
   contract, `File.currentIngestionGeneration`, or any field/route
   documented in [INTEGRATION.md](INTEGRATION.md)), update that document
   in the same PR — it must never describe a contract that no longer
   matches the code.
4. Write a PR description that states *why*, not just *what* — the diff
   already shows what changed.
5. Never include a real `.env`, `*.pem`, or any credential in a PR, even
   accidentally via a pasted log or screenshot.

## How to prepare for deployment

This project is currently local-development-only — see
[LIMITATIONS.md](LIMITATIONS.md) and [ROADMAP.md](ROADMAP.md) for exactly
what's not yet done. Before any real deployment:

1. Replace `.env` files with a real secret-management system for every
   value in [ENVIRONMENT.md](ENVIRONMENT.md) — never ship `.env` files.
2. Set `FILE_URL_REQUIRE_HTTPS=true` (Team4A) — the local-dev `false`
   override must not follow you into any real deployment.
3. Provision GPU-backed or hosted LLM inference — local CPU Ollama
   inference (30–140+ seconds/answer) is a development-environment
   characteristic, not acceptable production latency.
4. Provision managed/production-grade MongoDB, Redis ×2, and Qdrant
   instances instead of local Docker containers.
5. Decide on the two items [M6_STATUS.md](M6_STATUS.md) lists as
   genuinely pending architecture decisions (the `REPRO-SPOOF-5`
   residual, and the ingestion-trust-model question) — do not deploy
   without an explicit decision on both, even if the decision is "accept
   as documented."
